# Release Notes for Influx

## Unreleased

### Added
- **Every native Craft field type has a mapping strategy now.** Nine were still on the `DefaultField` fallback's raw `setFieldValue()`, which is the right write for a plain scalar and wrong for anything whose stored form isn't what a feed ships. Plain Text, Number and Email stay on it deliberately.
- **`Addresses` (Craft 5) wrote nothing at all** — the same silent no-op a ContentBlock had before alpha.8, and for the same reason: an address is a nested ELEMENT, and Craft's field only consumes its own serialized record shape, ignoring anything else without a word. The save reported success over an empty field. The new strategy is a fan-out over one shared layout — many records, one implicit type, so it sits between Matrix and Table — with one sub-mapping per slot: the 17 native address properties plus the Address layout's custom fields, each landing in the channel Craft reads it from (natives at the top level, custom fields under `fields`), index-zipped into as many addresses as the feed carries. An empty `countryCode` is skipped rather than written, because `Address::init()` has already defaulted it from `defaultCountryCode` and overwriting that with an empty string breaks a required property. Full-replace, like Matrix and Table.
- **`Link` (Craft 5.3) could only ever store a bare URL.** Craft reads a plain string as a URL-type link, so that much worked by accident and everything else was unreachable: no way to feed an entry link, a label, or a `target`. A link is several values, so the row is node-less like Table's and ContentBlock's, with one sub-mapping per slot and the envelope assembled here. Which slots exist is the field's business, not the feed's — the type select offers only the link types it allows, the label row appears only with `showLabelField`, and the advanced rows mirror its `advancedFields`. A type the field doesn't allow fails that row rather than the whole item, which is what Craft's own `InvalidArgumentException` would have done. This covers the deprecated URL field on Craft 5 too, since Craft aliases it onto Link; Craft 4's Url is a genuine string field and stays on the fallback.
- **A Preparse field says it can't be mapped, rather than offering a mapping that gets thrown away.** Its value is a Twig template the plugin re-renders on `EVENT_BEFORE_SAVE_ELEMENT`, walking every Preparse field on the layout unconditionally — so the template always wins, over a sync and over anything an editor types. A mapped one was worse than useless: the write was discarded on every save, and the row churned, because the stored value was the rendered template while the incoming one was the feed's and the two never matched. The row now keeps its label and says why, which is the treatment an entry's `uri` and a tag's `slug` already get for being derived on save. Lives under `integrations/jalendport/preparse` with the other third-party code, and is keyed by class string so an install without the plugin never touches it.
- **`Json` (Craft 5) stored a JSON string as a string.** Craft only decodes on the request path — the plain normalize a programmatic write goes through wraps whatever it's given verbatim — so a feed shipping `"{\"a\":1}"` stored a document whose entire value was that string. It looked right in the CP, where a string of JSON renders as JSON, and read wrong from Twig. Decoded first now, and compared with object keys sorted recursively so re-emitting the same document in another key order isn't a change. List order still counts: position is meaning in a JSON array.
- **`Money` was ambiguous about its own units.** Craft infers major-vs-minor from punctuation, so a feed shipping `20` for €20.00 quietly stored twenty cents while `20.00` stored twenty euros. A `units` option declares it instead. Major amounts parse through moneyphp's DECIMAL parser rather than Craft's `MoneyHelper::normalizeString()`, which binds an `IntlMoneyParser` to the site's formatting locale and on a Dutch or German site reads `19.99` as nineteen-thousand-odd — a feed is machine data and its decimal point means a decimal point.
- **`Country`** now reduces to the alpha-2 on both sides and can match on country NAMES through Craft's own repository, for feeds that ship "Belgium" rather than "BE". **`Color`** normalises every spelling of one colour to a canonical hex through Craft's own `ColorValidator`, and rejects a value that isn't one instead of letting the normaliser turn `red` into `#red`. Both offer their "use default" cell as a **select** rather than a text box, the way an option field already does — the world's countries for one, the field's own palette for the other — so an operator picks a value instead of remembering an alpha-2 or retyping a hex. A palette entry with no label labels itself with its hex; a Color field with no palette keeps a text box, since any hex is valid there. **`Icon`** strips the `fa-` prefix feeds carry and Craft's stored names don't — the CP's icon picker showed nothing for a stored `fa-user`. **`Range`** clamps to the field's min/max and snaps to its step, so the value Influx writes is one the CP's slider can represent.
- **A nested row is configured the way the same field is at the top level.** A sub-field row carried a default-value editor and nothing else, so a Matrix block's Assets child was stuck matching by asset ID whatever the feed shipped, with no control in sight to change it — and a `mode: url` already stored on that row was live, honoured on every sync, and unrenderable. Each row now carries its field's whole extras region behind its own disclosure, writing its own `options`: a nested Assets row's match-by and its upload toggle, a nested Date's format, a nested relation's match-by and sub-field card. None of that needed runtime work, because a sub-row IS a whole mapping the applier descends into — the extras were honoured all along, they just had nowhere to be set. A nested Matrix or Super Table stays the exception: its value is block cards a card can't nest, and that bound is also what makes a cyclic relation graph terminate.

### Fixed
- **A run could report errors nothing would let you find.** `error` was the one item action with no counter column, and the counter row IS the log viewer's item filter — so a run that threw on a dozen items finished `ok`, summarised itself as created/updated/unchanged, and offered no way to reach the rows that failed short of paging the whole list. Worse, the two places that answer "does this log have errors" disagreed: the CP nav badge counted a log whose run failed OR which recorded any error item, while the overview's Error filter matched on run status alone — so following the badge to the list left out the very logs it was counting. Errors have a counter now (back-filled for existing logs), which puts a red chip on the filter row and a red pill in both overviews, and the badge and that filter read one shared definition. A failed run and a completed run with failed items stay distinct facts; both are "needs a look", which is what those two are asked.
- **Checkboxes and MultiSelect were offered a single-value default picker.** One strategy covers the whole `BaseOptionsField` family and it declared the same select for all of it, so a default on a field that holds a LIST could only ever set one of the boxes. They get a multi-select now — picks accumulate, clicking one again removes it, and it stores nothing rather than an empty list, which a mapping would otherwise read as a default that IS set. Craft answers the arity publicly (`getIsMultiOptionsField()`) in 4 and 5 alike, so no version seam; the arities themselves are pinned by a spec that reads them off Craft's own classes, so a change upstream fails at the source rather than agreeing with a stale mock.
- **A Color field carried two Influx marks on the element editor**, the second one floating inside the input above the control. Several Craft field types build their input from a `Cp::*FieldHtml()` helper, which wraps it in a second `.field` whose id it derives as `"<inputId>-field"` — the id the outer wrapper already has. A Color field with a palette is one (`colorSelectFieldHtml`), so the page genuinely holds two `#fields-<handle>-field` nodes, and `querySelectorAll` returns both where `getElementById` would stop at the first. The probe keeps only the outermost match now, which is general rather than Color-specific. The editor asset also gained specs of its own — its DOM probing had none.
- **`Time` and `Money` re-saved their element on every single run**, cutting a revision each time. Both store a value the shared comparison normaliser can't reduce to the feed's shape — Craft normalizes a Time to a `DateTime` but serializes it to an `H:i:s` string, and a `Money\Money` is JsonSerializable rather than Stringable, so it reduced to `{"amount":"1999","currency":"EUR"}` against the feed's `"19.99"`. Both sides now reduce to one canonical form (a clock time, a minor-unit amount), the same fix `Date` carries for serialized dates. The alpha.9 roadmap described Money's symptom backwards — as updates being silently skipped — which is worth recording since it's the opposite failure.
- `Color`, `Country`, `Icon` and `Json` churned the same way for the same reason, less visibly: a `ColorData`, a `Country` model, an `IconData` and a `JsonData` all fell past the normaliser's scalar cases.
- **A user mapping offered a name shape the CP never shows.** Craft renders its Full Name layout element as EITHER one full-name input OR a First/Last pair, on the `showFirstAndLastNameFields` general config, and branches its own validation on the same setting — but the writable list carried all three unconditionally, so two of the rows on every Users relation card and every `UserTarget` mapping addressed something no editor could see or correct. Only the rendered shape is offered now, and none of the three when a module has stripped the element out of the user layout. Same `isFieldIncluded()` probe an asset's alt and title already went through.
- **An `Addresses` mapping offered all 17 of Craft's assignable address properties**, where an Address only exposes the ones its layout includes — on a stock layout that's four, so seven rows (the names, organization, tax id, latitude, longitude) were unmappable in the CP. The slots come off the layout now, with the two composite elements expanded: one `address` element stands for the whole country-specific block, one `latLong` for latitude plus longitude. A stored mapping for a native the layout has since dropped is skipped rather than written, the way Table skips a removed column.
- **The address card now reads like the address editor.** Its rows follow the layout's own order — so a site that rearranges its layout rearranges the card — and within the address block, Craft's render order rather than its deserializer's (administrative area before locality, not after). The labels are Craft's too, read off an Address element instead of spelled out here, which makes them country-aware the way the editor is: an `administrativeArea` reads "State" on a US-default site and "Province" on a Canadian one, a `postalCode` "Zip Code" or "Postcode", and `title` reads "Label". A site overriding a label through `Addresses::EVENT_DEFINE_FIELD_LABEL` gets it here for free.

### Changed
- **One declaration describes a whole mapping row now, and the CP renders it by lookup instead of by branching.** A field's UI was described by three mechanisms in two vocabularies — a loose `defaultEditor()` descriptor, a real `schema()` node list, and a bag of `fieldMeta()` flags — with nothing describing the source-node cell at all, which was hardcoded in Vue for every row. That cost three branch chains on control type (twelve conditions in `SchemaForm` duplicated across its two layouts, four more in `MappingRow`) and made `defaultType: "select"` and `schema[0].type: "select"` the same control rendered by different code. `schema()` returns a `MappingSchema` of three regions instead — `source`, `default`, `extra` — each `true` for the region's preset, a callback for any control with any config, or absent. Absence replaced both flags: a Matrix declares neither cell because its value comes from its sub-mappings, and a Preparse field declares a source region holding nothing but a `note()`. Every region renders through one `type => component` map, so adding a control kind is a Vue component and one registry line, and adding a mapping kind really is the single-PHP-file change the README claimed. Regions resolve lazily and memoize, which is load-bearing rather than a saving: a relation whose graph cycles used to recurse until it died.
- **A default-value select's empty row is a sentinel rather than one of the field's values.** It was being merged into the option list as a value labelled `—`, spelled independently in four places, which made an unset default announce itself as "—" where the source cell beside it showed nothing. It is declared on the node now, the way the source cell declares its own two: it sits in its own group above the field's values, it drops out of the list while the operator is searching, and picking it leaves the cell reading empty. Lazy lists get it too — the sentinel rides the node while the options ride the fetch, so it is pickable before the list resolves and the endpoint answering that fetch returns none of its own. Table's select columns came onto the same preset in passing, having had no search box at all.
- **A row's default-value select is the same control as its source-node one**, search box and all — a default list can run to a country's worth of options and had no way to search them. Not `allow-custom` though: a node path is open-ended, a default is a value the field itself declares. An empty select also shows nothing now instead of "Select…", so it reads like every other empty cell on the row; the callers that do want stand-in copy pass it (`— no mapping —`, `— none —`, …).
- **An Icon field's default cell mounts Craft's own icon picker**, the way an element default already mounts Craft's element select — grid, previews and all. Worth the round-trip more here than anywhere: Craft's set is some 3,800 icons, each with its own search terms and a Pro flag, and Craft already searches them SERVER-side from inside that control (which is why "car" finds "automobile"). A select over icon names would have shipped all of them to do a worse job with nothing to look at. Whether Pro icons are selectable is the field's own `includeProIcons`, derived server-side from the field handle for the same reason an element picker's sources are.
- **A default list can be fetched on first use instead of shipped.** A strategy declares `'lazy' => true` on its editor and answers `Field::defaultOptions()`, and the row fetches once when the operator first opens it (`influx/link-builder/default-options`). `Country` opts in: ~250 options that otherwise rode every builder bootstrap once per Country field on the layout, whether or not the row was ever touched. Options that ARE a field's own settings — an option field's, a colour palette — stay inline; they're already in memory, so deferring them would only buy a round-trip.
- Three strategies each carried their own copy of the same sub-mapping helpers; `filterActive()`, `coerceChildValue()` and `childStrategy()` moved to the shared `Field` base, where the fourth caller could reach them. No behaviour change — Matrix keeps its own `childStrategy()` seam by overriding the inherited one.
- The registry test now pins every built-in key, including Matrix, RichText and ContentBlock, which it never covered. The failure mode it guards is silent: a strategy that's written but never registered just falls to `DefaultField` and writes something plausible.

## 1.0.0-alpha.9 - 2026-08-03

### Changed
- **Every site the CP shows is a Craft chip**, labelled with the site's name rather than the handle its gray pill carried: the Links overview's Sites cell, the Logs overview's Site column, the log detail, and the per-site endpoint lines a multi-site run lists. Craft 5's chip renderer takes any component, not only elements, and a site is one. The Links cell shows the first site's chip plus a `+N` badge that reveals the rest on click, so a link on sixteen sites is one line instead of four. A link with no site endpoints — and a run with no site scope — chips the primary site itself, where both used to show a blue "primary" pill: the site it ran against is the fact worth showing. Craft 4 has no generic chip renderer and keeps a pill, carrying the same name.
- **The Logs overview names a run's link with its chip and the person who triggered it with theirs**, in a User column of its own beside the trigger. The user chip is Craft's own — photo, status, hyperlinked name — resolved for the whole page in one query, and a hard-purged account still reads as a muted `#id`. A link is a config model rather than an element, which Craft 5 chips just as happily; a run whose link has since been deleted degrades to the handle it stored, as it did before.
- **The log detail's run facts moved out of the summary sentence into labelled cells.** Site, trigger, user and window read as their own facts now — the site and the user as chips — laid out on the counters' grid, so a fact sits in the same column as the counter under it. The sentence beside the link keeps the timing and nothing else.

## 1.0.0-alpha.8 - 2026-08-03

### Added
- **A relation mapping offers the related element's own fields.** A card used to hold an entry's title and slug and nothing else; it now holds every custom field of the layouts the field's sources allow, on the same `fields` channel the runtime has always applied. Assets keep their volumes' custom fields — in ONE card now, together with alt and title, rather than two cards split by the write channel behind them. A row marks the channel it lands in, the way a Matrix block's Title row already did.
- **A sub-field row's default editor follows the sub-field's own type.** "Use default" became field-type aware in alpha.7 for top-level rows only, so a relation sub-field still asked the operator to retype a reference into a text box; each row now carries the editor its own field's strategy declares — an element picker for a relation, a select over its options for an option field. The picker mounts when its card is opened, so a mapping tab full of relation rows doesn't fetch one per row up front.
- **A Table mapping drills into its rows.** A Matrix row expands to a child per block; a Table row showed one flat blob of every cell it wrote. It now expands to a child per table ROW, its mapped columns as that child's cells, named after the column headings — the only place that knows `col1` is "Label". Rows pair the way blocks do: one identical to a stored row reads unchanged, the rest are rewritten by the full replace, and a stored row the feed no longer carries reads as removed. A table row is no element, so it carries no chip and is labelled by its position, which is its identity anyway.
- The details sidebar reports where the sample stands and how much of the field tree is mapped, and its **Auto-match** fills every field whose handle matches a node in the sample. It only ever fills a field that has no source node and no "use default", and the rows it filled carry an "auto" badge until they're touched.
- A source node can be typed in when the fetched page doesn't carry it — the picker offers the typed path as a "Custom node". It saves like any other node and reads as a missing mapping until a page carrying it is fetched.

### Changed
- **Alt text and Title are offered only where a volume's field layout includes them.** alpha.7's notes claimed they stay unconditional because they're element attributes; that's true of the write, but a row nobody can fill in the asset's own editor has no business in a mapping either. A mapping saved before this keeps applying — the schema is rebuilt from live layouts on every request, so dropping it would make merely opening a link destructive — and "clear nodes" removes it.
- **Only the missing-element policies that match the endpoint shape are offered:** the two global ones on a single-endpoint link, the two per-site ones once site-specific endpoints are on. Saving already rewrote a mismatched pair to its counterpart and said so in a notice; the checkboxes now say it up front.
- The mapping tree's per-row Clear is gone — the group header's "clear nodes" link is the single clear affordance, and reads as chrome rather than a link.
- A Table field's Columns card lost its instructions paragraph; the rows say what they do.
- **A status pill in the inspector explains itself in Craft's own tooltip.** It used to pop a hand-rolled dark card, anchored once at click time with no flip and no viewport clamping; the CP registers `<craft-tooltip>` for exactly this — floating-ui positioning, the CP's own light/dark theme, appended to the body so no overflow can clip it — and about forty lines of positioning and listener bookkeeping went with it. The explanation shows on hover and focus now rather than only on click, and is the pill's accessible name as well (Craft's tooltip sets no `role="tooltip"`, so a reader who can't see it would otherwise get "use default" and no way to reach the why). On Craft 4, which registers no such element, the sentence rides the button's own `title`.
- The log item list dropped its "In trash" pill — the row is about what the run did to the item, and the line already carries a title, a message and an action badge. The detail pane's Resource row keeps the pill, and a trashed element's chip stays unlinked: Craft's own chip refuses to hyperlink one, and the element edit screen never relaxes its `trashed` filter, so the URL would 404 until the element is restored.

### Fixed
- **A refused save's validation errors now sit on the rows they came from.** Craft reports them keyed by attribute path — `test_email`, or `test_matrix[new1].title` for a field on a nested element — and nothing read those keys: every message was JSON-encoded into the item's message, so an operator read a blob naming fields while the rows beneath it, which say exactly which node each value came from, showed nothing. Each message now lands on its own row, a nested one on the child's leaf row AND on the parent (which is collapsed by default and would otherwise read clean), and the item's message says how many there were instead of repeating them. Errors for fields the link doesn't map have no row to sit on, so the message still spells those out. They also count towards the item's error badge now, like a strategy error does.
- **Every native sub-field failed its row.** The guard in front of that write asked `$element->hasAttribute()`, an ActiveRecord method `yii\base\Model` — and so every Craft element — doesn't have, so it threw `UnknownMethodException` instead of answering, and the sub-mapping loop deliberately doesn't catch. Any mapping writing an asset's alt text or title, a related entry's title or slug, or a user's email or name errored with "Calling unknown method": the whole channel the sub-field cards write. It asks `canSetProperty()` now, with behaviours excluded so a custom-field handle can't be assigned straight onto the element behind the `fields` channel's back.
- **A ContentBlock field wrote nothing at all.** It had no strategy, so it fell through to the default one and stored whatever the node resolved to — and Craft's own field only consumes an array shaped `{fields: {handle: value}}`, ignoring anything else without a word. The save reported success and the block stayed empty. A dedicated strategy offers one sub-mapping per field in the block's layout and builds that envelope itself, so the feed never has to carry Craft's serialization shape. It also read as changed on every single sync (the stored value is a nested element, compared as its id against a JSON blob of the incoming array), and it offered a source-node picker for a value that only ever comes from its sub-mappings. Addresses and SEO-settings-style container fields are still on the default strategy — same shape, not yet investigated.
- **A relation read as changed on every sync when one of its ids pointed at a disabled, drafted or other-site element** — a save and a revision per run on an element the feed never touched. The stored side was read with `ids()` on the query Craft handed back, which still carries its own defaults (enabled only, one site, no drafts), so such an element silently dropped out of the stored list and the two sets could never match. The more ids a relation holds the likelier one is in that state, which is why it showed on multi-id rows. The query is relaxed exactly the way `BaseRelationField` relaxes it for serialization now. Same symptom, second cause: a field with `maintainHierarchy` has its gaps filled by Craft on save, so the stored side legitimately holds ancestors the feed never sent — that flavour is compared as a subset, where a change is the feed asking for an id the element isn't related to.
- **A native attribute mapped to "use default" logged no value at all.** A native row never carried a parsed value, which passed unnoticed for an attribute read from a node (both columns showed the feed value) but left a defaulted row looking like it had done nothing on the run where it wrote the default. The row reports its resolution now — the node's value, else the default — and not the stored form, which the target coerces per attribute and which the row's own current/changed columns already speak about.
- **A Users relation offered `slug` and `title`** — neither of which a user has, so a match on them could never resolve one — while hiding `username` and `email`. Every relation flavour now offers its own element type's identifiers, from one shared list the native Author dropdown and the link-level match key read too. Entries gained `uri`.
- **Categories, Tags and Users relations had no sub-fields card at all.** The rows were probed for by looking up a native field-layout element, and Craft ships one for an entry's title and for nothing else — which also meant no flavour ever offered a slug.
- **An Entries field limited to Single sections resolved no sources**, so it offered no match options, no sub-fields and no query scoping on its lookups: Craft stores that restriction as the bare key `singles` rather than as `section:UID`.
- The General tab never flagged red for "Add at least one site endpoint" — the error's attribute was missing from the tab's error map.
- The detail pane headed a hard-deleted element's row with nothing but an action badge, while the list beside it named the item. Both panes fall back to the same title now.
- The split inspectors' seam read as a striped border wherever a pane scrolled: Craft paints scrollbar tracks grey, so inside the pane whose inline-end edge IS the seam the track ran alongside the hairline as a second line. The track is transparent in those scrollers now, with a stable gutter so rows don't shift when it appears. The resize handle's hover state also stopped being a saturated full-height blue bar — hover thickens the seam in grey, and the blue is kept for a live drag and for keyboard focus.
- The two pane headers stepped at the seam: each declared its own floor, and the detail side holds an element chip whose own min-height pushed it past that. One token sets all four of those bars, above the tallest natural content.

## 1.0.0-alpha.7 - 2026-08-03

### Added
- **Log drill-down:** a mapping row in the run log and the debug inspector now expands to the elements it actually touched — the related entries, categories, tags, assets and users a relation field wrote, and a Matrix field's blocks paired per block so each one reports its own values instead of a flat list for the whole field. Every child carries its own action badge (added, removed, created, updated, unchanged, error — a new `ChildAction` vocabulary owns them and their colours), is labeled by its own title, and links to the element it points at.
- The drill-down is served from the rows the run itself produced, stored with the log item in a new `influx_log_items.mappings` column. It used to be re-derived by a dry run at view time, which reads the element's *present* state — so a successfully-updated item showed "no change" on every row, and a run-time failure couldn't be reproduced at all. Items logged before this release keep a null column and render flat with a notice; the data only exists at run time, so no back-fill is possible.
- **Run attribution:** a run now records who asked for it, not just the mechanism it started by. The overview shows the username under the trigger pill and the log detail reads "by <name>", with the trigger rendered as its label instead of its raw value. A `RunOrigin` value object carries the mechanism plus the user id captured at trigger time (inside a queue job the current user is whoever drains the queue, so it can't be read there) to a new nullable `influx_logs.userId` — deliberately without a foreign key, since a cascade would erase the attribution the column exists to keep.
- **Table fields are mapped column by column.** They fell through to the default strategy and stored whatever the node resolved to, verbatim. A dedicated strategy offers one sub-field row per column — keyed by column ID, the only key Craft's serializers read and the only one that survives a handle rename — and zips the per-column value lists into rows the way Matrix zips its blocks. Only mapped columns are fingerprinted, normalised per column type, so a CP-stored bool or `DateTime` doesn't read as a change against the feed's `"yes"` or ISO string.
- **An asset mapping offers the volumes' own custom fields.** The runtime has applied custom sub-fields on assets all along; the builder only ever offered the hardcoded `alt` and `title`. Asset cards now carry an "Asset fields" group built from the union of the field's allowed volumes' layouts (deduped by handle, first layout wins). `alt` and `title` stay unconditional — they're element attributes, writable whatever the layout says.
- A Matrix block type's native **Title** is offered in the mapping tree. The engine has written `blocks.<type>.nativeFields.title` all along, but the schema never offered it; a block type that has a title field now leads its card with a Title row. A Craft 4 Matrix block has no title, so nothing is offered there.
- **"Use default" gets a field-type-aware editor.** Relation fields (entries, users, categories, tags, assets) get the same element picker the native Author field has, option fields get a select over their own options, everything else stays a text input. The picker is shaped after the field it picks for — its own sources, or the single source of a Categories or Tags field, and single versus multiple per `maxRelations` — read off the same settings the sync scopes its lookups by, so a pickable default is a resolvable one. A picked default is an id, so it's matched by id whatever the row's "Match by" says, and never created on a miss.
- **Clearing a mapping takes one click.** A mapping group's header carries a "clear nodes" link that wipes every mapping in the group, each sub-field card header carries its own, and a row-level Clear fades in when the row is hovered or focused. No confirmation step — it's an in-memory edit the builder's dirty guard already protects.
- The split list in the log viewer and debug inspector can be resized by dragging the seam between the two panes.

### Changed
- **Elements are saved with validation on**, reversing the policy alpha.6 shipped (`ElementTargetInterface::save()`'s base implementation is now Craft's own default save). Skipping validation was costing more than it bought: Craft does real work in there, and the case that surfaced is `SlugValidator` deriving a slug from the title — every element Influx created carried `slug` NULL, and with it `uri` NULL, so no front-end URL at all. Feed Me has always saved with validation and these feeds run through it in production, so the data is known to pass. The trade is that a value Craft rejects now fails the row with an error instead of being forced into a state Craft considers invalid — the louder of the two failures. Coercion on the way in still handles the common feed messiness first, so it rarely reaches the validator.
- The date-format hint under a date mapping's options is gone; it explained `createFromFormat` and `DateTimeHelper` to an editor, and the option labels say enough on their own.
- The README documents which field types have a dedicated strategy and which are still served by the `DefaultField` fallback (including the two whose fallback behaviour is wrong — Time churns every sync, Money never updates after the first write), and a short Concurrency Q&A covers what the `influx:sync:{handle}` lock does and doesn't guarantee.

### Fixed
- **Data loss:** on Craft 5, a Matrix field's child values were dropped — the run reported `ok` with no errors while writing empty blocks over populated ones. The throwaway block the strategy builds to read a layout was constructed from `typeId` alone, and a nested entry without `fieldId` can't resolve an owner, so every property read threw and every child was skipped. Because the block *count* comes from the resolved child lists, the output looked right: a feed of two rates produced two blocks, with every value gone. Only the Craft 5 branch was affected. It also made Matrix fields permanently dirty, since the incoming fingerprint was all-nulls.
- **Retired the element in every site:** a link that fans out over sites shares one canonical element, so a mapped `enabled` — most commonly a per-language `/deleted` endpoint — wrote the whole-element flag and pulled the element from every other site with it. A head-to-head against Feed Me on the same restored baseline disagreed on all nine items. A link with per-site endpoints now writes the status of the site being processed and derives `enabled` as "enabled in at least one site", which is how Feed Me resolves the same mapping; a link with one endpoint for everything is speaking about the element as a whole, so it still writes the whole-element flag and lets the section's propagation carry it. The scope comes from the link's endpoint shape rather than from the element, because a cross-site lookup resolves through `siteId('*')->unique()` — `$element->siteId` was whichever row Craft happened to return, so the status landed on an arbitrary site. Same comparison afterwards: no disagreements.
- **Silently thinned relations:** when a related element the feed also creates was refused by validation, the reference contributed nothing; with every reference failing, the parse returned null and the field was written as `[]`, detaching the element's existing relations. Seen live with tag names matched by the default `id` key, then colliding on title at create. A refused create now fails the row instead.
- Date-only values gained the site's UTC offset. A timezone-less `2026-07-07` was read as UTC midnight, so on a site in Europe/Brussels every date shifted two hours and rewrote itself on every sync. The ambiguous case now assumes the system timezone; a value carrying its own offset was already correct and is unaffected.
- A Matrix field replaced its blocks on every sync when any mapped leaf was null: a child resolving to null contributes no per-block value, while the stored side returns every requested handle whether it holds a value or not, so one fingerprint printed `{"description":null}` and the other printed nothing. Both sides now print every mapped leaf, missing ones as null — which is what the saved block holds.
- Rich text read as changed on every sync when the feed's HTML ended in whitespace: the incoming value was compared against the stored content, which the field trims on save, so identical markup differed by one trailing byte. Both sides are trimmed now.
- A relation read as changed on every sync when its node path collapsed across parent rows — `sessions.…room.location.id` on an eleven-session activity resolved the same location eleven times and handed the field the same id eleven times, which Craft relates once. Parsed relations are de-duplicated in first-seen order, so the written value is right and not just the comparison.
- **A bad root node left a new link with no way forward:** the feed sample computed its root-node candidates and then threw them away when the configured root node couldn't resolve a list, so a fresh link against an enveloped feed reported a failure and offered nothing to pick from. The report degrades to a partial one now — candidates plus a warning, shown on the fetch button and under the Root node select — and picking a candidate refetches into a full report. An empty node list also reads as "can't know" for the missing-mapping checks instead of "every saved node is missing".
- Log rows kept pointing at their element while it sits in the Trash. Influx's own deletes are soft, but every log lookup used the element query's default `trashed=false`, so a run's deleted rows degraded to a bare `#id` the moment the sync finished. Trashed elements are loaded in the log presenters and the drill-down, flagged with an "In trash" pill, and — on Craft 4's emulated chips as on Craft 5 — not hyperlinked. A hard-deleted element's row prefers its match value over an id pointing at nothing.
- A drill-down snapshot was dropped whole when one value held invalid UTF-8 (the element's own stored content, not the feed), and the flat view then claimed the row predated snapshot storage. The offending value is dropped with a warning and the rest of the snapshot is kept.

## 1.0.0-alpha.6 - 2026-07-29

### Changed
- Queue job descriptions read as sentences naming the link, the sliding-window preset and the site — "Importing Units with 1day for site Durabrik - NL" — instead of a handle with `(site: …, preset: …)` appended. Each clause is part of a translatable sentence now rather than concatenated outside the translation, and descriptions and progress labels are lazy-translated (`Translation::prep()`), so a queue row reads in the viewer's own language rather than the language of whoever triggered the run.

### Fixed
- **Progress never moved:** a queued sync reported progress once per feed page, but a queued run walks one page per job — so the only report landed as the job was about to finish and the bar sat at 0% for the whole of every step (an unpaginated feed is a single job, so the entire run showed 0%). Progress is reported per item now, throttled to whole-percent movements, and its cumulative count is carried across steps so a re-queued page resumes the percentage instead of restarting. It also no longer depends on `loggingEnabled`, which pinned the numerator at 0 when logging was off.
- A run log's "seen" counter counted log ROWS, not feed items: it also counted every element the missing-elements sweep disabled or deleted (elements that by definition weren't in the feed), sweep-bail notices, and an item that logged twice. It counts the items the feed actually contained now; swept elements remain in the "disabled" / "deleted" counters.

### Added
- **Field indicator:** a small Influx glyph now marks every field an active mapping writes, on the edit screen of any targeted element. Its tooltip explains the value is set by synchronisation, so an editor sees at a glance which values are Influx-managed and may be overwritten on the next sync.
- Extension points can be registered imperatively as well as by event: `Influx::getInstance()->targets->register(MyTarget::class)`, likewise `->fields->register()` and `->auth->register()`. Registering a class that doesn't satisfy the extension point now fails loudly instead of being dropped.
- `SchemaBuilder::node()`, an escape hatch for a mapping-extras control the builder doesn't ship a node type for. The CP renders an unrecognised type as a labeled text input on the node's handle rather than dropping it.
- The endpoint-token allow-list is overridable, so a plugin can substitute tokens for field types Influx doesn't allow by default.
- Enum owners for the run-status, item-action and missing-element-processing vocabularies (`RunStatus`, `ItemAction`, `ProcessingAction`, `RunFailure`), plus a `schema` namespace holding `SchemaBuilder` and a typed `MappableField` descriptor.
- The CP's action colours and log counters are derived from those enums and shipped to the Vue apps in each app's bootstrap config, instead of being hand-maintained in the JavaScript.
- `ElementTargetInterface::supportsSweeping()` — a third static capability beside `supportsMultiSite()` and `criteriaKeys()`: whether links to this element type can be swept for elements missing from the feed. Targets extending `AbstractElementTarget` need no change; one implementing the interface directly must add it.
- `ElementTargetInterface::save()` — the engine's element write routes through the target now, like the four destructive writes already did, so a third-party target can save with whatever flags its element type needs. The base implementation is Craft's own save with validation off (the feed is authoritative — the same policy Feed Me imports run on).
- `ElementTargetInterface::claimCells()` — a target describes how its element type partitions, so a custom element type reports a real claim scope instead of the "everything" sentinel that made any two links of that type warn as overlapping. Entry's section × entry-type expansion moved from `Link` onto `EntryTarget`.
- `Link::criterion($key)`, the one reader for stored `elementCriteria`, with the key names owned as constants by the target that declares them (`EntryTarget::CRITERIA_SECTION` / `::CRITERIA_TYPE`). Stored config is untouched.

### Changed
- **Breaking:** the endpoint-token events follow Craft's `EVENT_DEFINE_*` convention. `EndpointTokensService::EVENT_REGISTER_ENDPOINT_TOKENS` → `EVENT_DEFINE_ENDPOINT_TOKENS` and `EVENT_REGISTER_ENDPOINT_TOKEN_SUGGESTIONS` → `EVENT_DEFINE_ENDPOINT_TOKEN_SUGGESTIONS`; the payload classes `RegisterEndpointTokensEvent` and `RegisterEndpointTokenSuggestionsEvent` are now `DefineEndpointTokensEvent` and `DefineEndpointTokenSuggestionsEvent`.
- **Breaking:** the targets, fields and auth registries share one API. `FieldsService::registerClass()` is now `register()`, and `AuthService::strategies()` is now `all()`.
- **Breaking:** `SchemaBuilder` moved from `GlueAgency\Influx\helpers` to `GlueAgency\Influx\schema`.
- **Breaking:** `ElementTargetInterface::getMappableFields()` returns a list of `schema\MappableField` objects instead of plain arrays.
- **Breaking:** `DebugService::streamSite()` is now `inspectSite()`; inspecting a stored log item moved to `InspectorService::inspectStoredLogItem()`.
- **Breaking:** the sync engine's collaborators moved into `sync\item` (the per-item pipeline) and `sync\run` (per-run orchestration). `SynchronizationService`'s own public methods and all five sync events — constants, sender, firing order and cancel semantics — are unchanged.
- Every JSON route answers a failure with the same envelope: `{success: false, message}`, plus `type` (the exception's short class name) for an uncaught error or `errors` for a validation failure.
- Queuing a sync for a link that doesn't take a pre-run backup no longer enqueues an extra job to take one.
- `Link::claimScope()` delegates its cells to the link's target; the model no longer branches on `craft\elements\Entry` or reads project config itself.
- Field strategies and the mapping walk resolve strategies (and their sub-mapping walk) through the `FieldContext` they're handed instead of reaching the plugin singleton mid-walk, which also removes the applier ↔ field-registry construction cycle. `MappingApplier` takes an optional strategy-resolver callable, `Matrix::childStrategy()` takes the context as its first argument, and `InspectorService` accepts an injected `ItemProcessor`.

### Removed
- **Breaking:** `Link::PROCESSING_*`, `Link::ALL_PROCESSING` and `Link::PROCESSING_SITE_COUNTERPARTS`. The `ProcessingAction` enum owns the processing flags, and their defaults, per-site counterparts, labels and pill colours all derive from it.
- The `pending` run status, which was never written. A run is `running`, `ok` or `error`.

### Fixed
- **Data loss:** queuing a sync for a single-site link enqueued an unscoped job, which fetched the wrong feed and could sweep missing elements across every site instead of the link's own. Site expansion now happens up front.
- **Silent no-op:** a User link's builder offered "Disable missing" / "Delete missing", but users can't be swept (no scope to enumerate) — the run did nothing and reported nothing. Those checkboxes are no longer offered for an element type that can't sweep, and a link still carrying one from older config gets a skipped row in the log explaining why.
- A related element that refuses to save — a category, tag or entry the feed also fills, rejected by validation — no longer passes silently: the mapping row now errors with the element's id, title and validation messages, so the log drill-down shows why the related values didn't change. Previously the save's result was discarded and the parent row reported success over stale values.
- URL-mode asset matching now really prefers the asset whose URL matches the remote one exactly. The preference was unreachable — the lookup had already collapsed to a single row — so a same-filename asset from another folder could be linked while the exact match sat one row away. A same-filename asset is still the best-effort fallback when no URL matches (a CDN/host change doesn't force a re-download), and a volume that exposes no URLs no longer aborts the comparison.
- A failed save logged `[]` as its reason. Syncs save with validation off by design, so the element's error bag is normally empty on failure; the row now says Craft refused the save without validation errors (a `beforeSave`/`afterSave` handler), and still reports real errors when there are any.
- `UserTarget` memoized the user-group handle → id map on the registry's shared prototype, so a group created mid-process stayed invisible for the rest of a worker's lifetime. The memo lives on the run's `SyncContext` now, next to the element-lookup cache.
- A long-running queue worker accumulated one dead log-item buffer per log id it ever wrote: flushing emptied the buffer but never dropped its map entry. Buffers are released when a run finishes, fails, or its log is deleted.
- A Matrix field with a lightswitch sub-field counted as changed on every run — the stored `1` / `0` was compared against the feed's `true` / `false` — so the element was re-saved each sync.
- Likewise for a date sub-field: Craft hands a stored date back serialized as a string while the feed's is a `DateTime`, so the two never matched. Both sides of a sub-field comparison now normalise through the strategy that owns that field type, so the same instant compares equal whichever shape it arrives in.
- A queued run's progress denominator shifted mid-run: the queued page loop sized its estimate from the current page while the synchronous one used the first page, so a short final page changed the reported total. Both use the first page's size now.
- "Disabled for site" rows in the run log and debug inspector render red, like their deleted counterpart.
- Link-builder strings missing from the server-side catalogue now translate, and stale entries are gone. The catalogue is pinned to the Vue sources by a test, so it can't drift again.
- The run-log viewer and debug inspector were untranslatable: they install the same translation helper as the link builder, but no catalogue of their strings was ever registered, so every label they render themselves stayed English on a translated control panel. Both apps — and the components they share — now ship a catalogue of their own, registered by the screen that mounts them and pinned to the Vue sources by the same kind of test. The log viewer's status filter also names the active counter with the label the server already translated, instead of the raw action value.
- The nav and plugin-store icons render in full again. The previous mark was stroke-based and Craft's icon-mask rendering zeroed its strokes, collapsing it to an underscore.
